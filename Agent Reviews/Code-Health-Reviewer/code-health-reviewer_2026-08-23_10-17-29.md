# Code Health Reviewer — 2026-08-23 10:17:29

Full-codebase (not diff) audit of the Oneness Yoga Trainers App for dead code, redundant/duplicated code, and non-optimal implementations. Read-only review; no application code was modified.

## Backend

### High

1. **Dead route: `POST /api/sessions/bulk` is no longer called by anything.**
   File: `backend/src/routes/sessions.js:168-198`.
   This handler (bulk-create sessions for week scheduling) has no caller anywhere in the frontend (`frontend/src/**` was grepped for `sessions/bulk` / `client.post('/sessions...` — only the single-session `POST /sessions` is used, from `AdminSessions.jsx`). It looks like leftover scaffolding from before the recurring `SessionTemplate` + `sessionGenerator.js` mechanism (added in the "recurring session schedule" commit) took over bulk session creation. It's still reachable (any authenticated super_admin token could POST to it) and still exercises `createMany` with no length cap, so it's not just inert — it's an un-tested, unreferenced surface that will silently rot (e.g. if the `Session` schema changes, nothing will catch a break here since no test/UI path exercises it).
   **Fix:** confirm with the team it's unused, then delete the route (and update any Postman/API docs). If it's kept intentionally as an admin bulk-import API, add a comment explaining who calls it and add basic length/rate limits.

2. **`frontend/src/pages/admin/Dashboard.jsx:25` — dead destructured variable `pushError` is never read**, only `enablePushNotifications`, `supported`, `permission`, `isEnabling` are used later in the component. This is harmless today, but it hides a real gap: if `enablePushNotifications()` rejects, the admin dashboard swallows the error via `.catch(() => {})` at the call site (line 193) and never surfaces `pushError` to the user, unlike `usePush`'s intended contract. **Fix:** either render `pushError` (e.g. a small inline error message under the banner, matching the trainer Dashboard's pattern) or drop the unused destructure to reduce noise.

### Medium

3. **Trainer-existence validation is duplicated three times with near-identical logic**, and will drift as the rules evolve (e.g. the recent "trainer must be active" checks were added to some but not all copies):
   - `backend/src/routes/sessions.js:31-44` (`ensureTrainerExists`)
   - `backend/src/routes/sequences.js:45-54` (`ensureTrainerExists`)
   - `backend/src/routes/sessionTemplates.js:44-58` (inlined equivalent logic)
   - `backend/src/routes/sessions.js:172-181` and `backend/src/routes/sequences.js:173-182` also each re-implement the "bulk trainer ids must all exist and hold the trainer role" variant independently.
   All four check `roles.includes('trainer')` via a fresh `prisma.user.findUnique`/`findMany`, but the error messages and null-handling differ slightly (e.g. `sessions.js`'s version tolerates `null` early-return, `sequences.js`'s does not). A future rule change (e.g. "must also be `is_active`") would need to be applied in 3-4 places and is easy to miss in one.
   **Fix:** extract a single `ensureTrainerExists(id, { allowNull })` and `ensureTrainersExist(ids)` helper into `backend/src/utils/trainers.js` and import it from all three routes.

4. **Serialization helpers duplicated per-route instead of shared.**
   `sessions.js:46-64` (`serialize`/`serializeWithZoom`), `sequences.js:77-84` (`serialize` + `withNames`), `leaves.js:22,33-37` (inline `{...l, x_name: ...}` mapping), `resources.js:40` (inline `creator?.name`), `sessionTemplates.js:29-32` (inline). Each strips a Prisma relation object and re-exposes it as a flat `_name` field — the same shape-transform, reimplemented per model. Not a bug today, but it means the "flatten relation to `<field>_name`" convention has no single source of truth, so a schema-serialization bug fix (e.g. escaping/localizing names) must be replicated everywhere. **Fix:** a small generic `flattenRelation(obj, { relation: 'assigned_trainer', as: 'trainer_name', pick: 'name' })` helper would remove ~40 lines of repeated inline destructuring across 5 route files. Low urgency — worth doing opportunistically, not urgent.

5. **`backend/src/utils/mail.js` repeats the same "no `resend` configured → warn and return" guard and the same `resend.emails.send({...})` call shape in all four functions** (`sendWelcomeEmail`, `sendGoogleLinkPendingEmail`, `sendGoogleLinkDecisionEmail`, `sendBackupAssignedEmail`, lines 5-74). Each hardcodes `process.env.RESEND_FROM_EMAIL || 'onboarding@resend.dev'` and the same `if (!resend) { console.warn(...); return; }` preamble. **Fix:** factor a `sendEmail({ to, subject, html, warnContext })` wrapper that does the guard + the `resend.emails.send` call once; the four public functions become one-liners building `{to, subject, html}`. This doesn't change behavior/usability, just removes ~20 duplicated lines and one place to fix if the Resend API shape ever changes.

6. **`users.js` `PUT /:id` doesn't normalize or validate email uniqueness, unlike `POST /`.**
   File: `backend/src/routes/users.js:59-82`. `POST /users` (line 44) lowercases/trims the email and explicitly checks for an existing user with a friendly `409 Email already exists`. `PUT /users/:id` (line 74) passes `email ?? user.email` straight into `prisma.user.update` with no lowercasing/trim and no pre-check. Two failure scenarios: (a) an admin edits a trainer's email to one that already exists (case-sensitively different, e.g. `Foo@x.com` vs `foo@x.com`) — Postgres's unique index on `email` is case-sensitive, so this silently creates two accounts that a human would consider duplicates, breaking login-by-email lookups elsewhere (`auth.js` always lowercases on login, so the newly-cased address could become permanently unreachable at login); (b) an exact-duplicate email throws an unhandled Prisma `P2002` unique-constraint error, which flows to the generic error middleware (`index.js:46-54`) and returns the raw Prisma error message (`Unique constraint failed on the fields: (email)`) instead of the friendly message the POST path gives.
   **Fix:** mirror the `POST` path — lowercase/trim `email` and check-then-409 (or catch the P2002 and translate it) before the `update` call.

### Low

7. **`resources.js` breadcrumb builder does one sequential DB round-trip per ancestor folder** (`backend/src/routes/resources.js:26-37`), walking up the tree one `findUnique` at a time instead of a single recursive CTE or a batch fetch. For the current shallow folder depth (a handful of levels) this is not a practical performance problem, but it's an N+1-shaped pattern that will get slower linearly with folder nesting depth if the resource library grows. **Fix (optional, low priority):** not urgent given current shallow nesting; if folder depth grows, replace with a single `$queryRaw` recursive CTE or store a materialized `path` column.

8. **`backend/src/middleware/auth.js:17-22` has a self-documented TODO to remove the legacy singular-`role` JWT fallback "after 2026-08-27."** Today's date is 2026-08-23, so this is 4 days from its stated removal window — not urgent, but flagging so it isn't forgotten past the stated date (stale multi-role migration shims left indefinitely are a common source of "dead branch that nobody dares delete" debt).

9. **Unused exports from `backend/src/utils/aiScheduler.js`:** `SESSION_TYPES` and `DAILY_LIMIT` are exported (line 287) but never imported by any other backend or frontend file (only used internally within `aiScheduler.js` itself). Not harmful, but dead surface area that suggests an earlier plan (e.g. sharing the type list with the frontend `TopicSelect`) that never happened — see also the duplicated-topic-list note in the Frontend section below. **Fix:** drop the two names from the `module.exports` if nothing external needs them, or use them from the frontend if the intent was to share a single source of truth.

10. **Dependency health — Resend, `dotenv`, `googleapis`, `google-auth-library`, `bcryptjs`, `express-rate-limit` are all one or more minor/major versions behind** (`npm outdated` in `backend/`): `bcryptjs` 2.4.3 → 3.0.3 (major), `dotenv` 16.6.1 → 17.4.2 (major), `googleapis` 173 → 176, `google-auth-library` 10.9.0 → 11.0.2 (major), `resend` 6.17.2 → 6.22.0, `express-rate-limit` 8.6.0 → 8.6.2. `npm audit` also flags 5 high-severity transitive vulnerabilities (`brace-expansion`, `deepmerge-ts` via Prisma's dev tooling, `ip-address` — likely pulled in via `googleapis`/`google-auth-library`). None of these are in the hot request path for unauthenticated input, so risk is currently low, but they're worth a scheduled bump. Not fixed as part of this audit per the read-only/no-behavior-change constraint.

## Frontend

### High

11. **`frontend/src/pages/admin/Leaves.jsx:28-34` — the `review()` handler has no try/catch**, unlike every other mutating handler in the codebase (which all wrap `client.*` calls in try/catch + `getApiErrorMessage`, e.g. the same file's sibling pages `trainer/Leaves.jsx:27-42`, `admin/Sessions.jsx:56-78`, etc.). If the `PATCH /leaves/:id/review` call fails (expired token, network blip, the leave already reviewed by someone else returning 404, etc.), the promise rejection is unhandled, no error message is shown, `showToast` still fires optimistically-looking code paths don't run (the toast is after the await, so it won't show on failure) — but the modal never closes since `setReviewing(null)` also never runs, leaving the admin looking at an unresponsive "Approve/Reject" modal with no feedback about what went wrong. **Fix:** wrap the body in try/catch like the other review/mutation handlers in this app and surface `getApiErrorMessage(err, ...)` near the modal buttons.

12. **`frontend/src/pages/Notifications.jsx:33-37` — `markAllRead()` shows a success toast unconditionally**, even when the underlying request fails: `await client.patch('/notifications/read-all').catch(() => {})` swallows the error, then the very next lines always run `showToast('All Notifications Marked as Read')` and `load()`. If the PATCH genuinely fails (e.g. token expired mid-session, transient 5xx), the user is told the action succeeded when nothing changed server-side — a misleading-success bug, not just a missing-error-message gap. **Fix:** check the resolved/rejected outcome (e.g. `try { await client.patch(...); showToast(...); } catch (err) { showToast(getApiErrorMessage(err, 'Failed to mark all as read')); } finally { load(); }`) so the toast reflects what actually happened.

### Medium

13. **`frontend/src/components/NotificationBell.jsx:26-38` hand-rolls its own polling (interval + `visibilitychange` listener) instead of using the existing `usePolling` hook** (`frontend/src/hooks/usePolling.js`), which was written to do exactly this (interval + refetch-on-visible, with a ref to avoid stale closures) and is already used consistently by every other page in the app (Dashboard, MySessions, Sessions, Sequences, Leaves, Resources, Notifications page, etc.). The bell's copy is functionally equivalent but is a second, independently-maintained implementation of the same pattern — if `usePolling` is later hardened (e.g. to pause while the tab is backgrounded, or to add jitter/backoff), the bell won't get the fix. **Fix:** replace lines 26-38 with `usePolling(refreshCount, 30000)`; the existing `useEffect(() => { refreshCount(); }, [location.pathname, refreshCount])` for on-navigation refresh can stay as-is alongside it.

14. **`AdminSequences.jsx` and `sequence-creator/Sequences.jsx` are ~85% duplicated page components** (`frontend/src/pages/admin/Sequences.jsx` and `frontend/src/pages/sequence-creator/Sequences.jsx`, both ~230-410 lines). Both implement: identical `load`/filter/week-selector state and effects (lines 17-65 in each), an identical "Add/Assign Sequence" modal form (topic/date/trainer/instructions), an identical `notifyWeek()` handler, and identical empty/loading/error states —差 differing only in the AI-schedule button/modal (creator-only) and the delete button (admin-only) and some copy/casing differences. This duplication means every fix to the shared list/filter/create logic (e.g. the topic-select `required` validation, or the trainer-id `Number()` guard added on line 72-76/83-87 of each) has to be made twice and can silently drift (worth checking they're still in sync). **Fix:** extract a shared `useSequencesList({ scope })` hook or a shared `<SequenceListPage>` component that both admin and sequence-creator screens compose, with the AI-schedule and delete-button bits as optional slots/props. This is a meaningful refactor, so treat it as a backlog item rather than a quick patch — flagging per the audit brief, not recommending an immediate large rewrite.

15. **`AdminSessions.jsx`'s "Assign Trainer" and "Assign Backup Trainer" modals are a near-exact duplicate of each other** (`frontend/src/pages/admin/Sessions.jsx`): `openAssign`/`submitAssign`/`assignFor`/`assignTrainerId`/`assignSubmitting`/`assignError` (lines 33-36, 104-128, 264-291) mirror `openBackup`/`submitBackup`/`backupFor`/`backupTrainerId`/`backupSubmitting`/`backupError` (lines 29-32, 80-102, 293-317) field-for-field, differing only in which API field (`assigned_trainer_id` vs `backup_trainer_id`) and endpoint (`PUT /sessions/:id` vs `PATCH /sessions/:id/backup`) they hit. **Fix (low risk, optional):** a small `useTrainerAssignModal({ field, submit })` hook or a shared `<AssignTrainerModal>` component parameterized by title/endpoint would cut this in half; not urgent since the current duplication is contained to one file and easy to reason about.

16. **`admin/Resources.jsx` and `trainer/Resources.jsx` duplicate the entire breadcrumb-navigation + folder-browsing logic** (load/breadcrumb rendering/folder click handling is byte-for-byte similar between `frontend/src/pages/admin/Resources.jsx:23-37,77-89` and `frontend/src/pages/trainer/Resources.jsx:14-53`), with the admin version adding create/delete. This is the same "two role-specific pages sharing 80% of one feature" pattern as items 14-15. **Fix (optional):** extract a shared `useResourceBrowser()` hook (load/breadcrumb/folder-nav state) that both pages consume, leaving only the admin-only create/delete UI as page-specific.

17. **Two independently-maintained "list of session/sequence topics" exist and can drift**: the full topic catalog lives in `frontend/src/components/TopicSelect.jsx:5-106` (`TOPIC_GROUPS`, ~50 topics across 9 categories), while the backend's AI scheduler keeps its own smaller, differently-grouped list in `backend/src/utils/aiScheduler.js:33-72` (`SESSION_TYPES`, ~30 topics across 3 categories) used to validate the AI's response (`aiScheduler.js:254`). Some entries exist in one list but not the other (e.g. `TopicSelect` has "Ashtanga Vinyasa", "108 Surya Namaskaras", "Kids Yoga", "Partner Yoga" that don't appear in `SESSION_TYPES`). This may be intentional (the AI scheduler is deliberately restricted to a curated subset), but if that's not deliberate, a topic added to one list silently won't show up as a valid AI suggestion (or vice versa) with no error to alert a maintainer that the lists disagree. **Fix:** if the AI subset is intentional, add a one-line comment in `aiScheduler.js` saying so (to stop a future maintainer from "fixing" the mismatch by duplicating the full list); if it's not intentional, derive `SESSION_TYPES` from (a subset of) `TOPIC_GROUPS` via a shared JSON/constants file instead of hand-copying.

### Low

18. **Frontend dependency health**: `npm outdated` in `frontend/` shows `axios` 1.17.0 installed vs. 1.19.0 wanted/latest, and `npm audit` reports **10 high-severity axios advisories** resolved by that same wanted version (e.g. GHSA-42h9-826w-cgv3 DoS via `formDataToJSON` recursion, GHSA-mmx7-hfxf-jppx prototype pollution in request construction, GHSA-xj6q-8x83-jv6g prototype-pollution-to-Basic-auth-injection). Because `axios` is the single HTTP client used for every API call in the app (`frontend/src/api/client.js`), and the fix is within the existing semver range (`^1.x`, no major bump), this is the one dependency finding in this audit worth prioritizing over the others. Also flagged: `form-data` 4.0.0-4.0.5 (transitive, CRLF injection, high) and `react-router`/`react-router-dom` (moderate, open-redirect + SSR deserialize issues — the app doesn't use SSR, so the second advisory doesn't apply, and `react-router-dom` is pinned well below the vulnerable range's own major-2 jump). Not applied here per the read-only constraint (`npm audit fix` would require running an installer command); recommend running `npm audit fix` (non-breaking within `^1.x`/`^6.x` ranges) in a normal maintenance window.

19. **`frontend/vite.config.js` has no manual `build.rollupOptions.output.manualChunks`**, so the whole app (React, react-router, axios, date-fns, all pages for all three roles) ships as one JS bundle rather than being split by route. Given the app's current size this is unlikely to be a real problem yet (no measured bundle-size complaint), and the PWA's precache-everything strategy (`vite-plugin-pwa` `injectManifest`) somewhat relies on a small, stable file set — so this is a low-priority "watch, don't fix yet" item, not a correctness issue.
