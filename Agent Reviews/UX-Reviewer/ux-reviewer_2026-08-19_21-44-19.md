**Date/Time:** 2026-08-19 21:44:19

## Scope
Independent certification of the fix for: "an already-logged-in user landing on a non-root URL via a genuine fresh app load should be redirected to `/` (home dashboard), while a same-tab refresh mid-session must NOT be disruptive."

- Login: super_admin `admin@oneness.yoga` / `admin1234`
- Tool used: Playwright (Chromium), driven by a local Node script since no interactive browser MCP tool was available in this session. Browser binaries were already cached at `C:\Users\manoj\AppData\Local\ms-playwright`, so `playwright@1.62.1` was installed on-the-fly into the session scratchpad (`.../scratchpad/pw-test`) purely as a test harness — no application code was touched.

## Code reviewed
`frontend/src/App.jsx`, function `useRedirectHomeOnFreshBoot(user)`:
- Uses a `sessionStorage.getItem('appBooted')` guard inside a `useEffect` with an empty dependency array.
- On the very first run per real JS page load, if `appBooted` is not yet set, it sets it and then — if the user is authenticated, not already on `/`, and the URL isn't a notification deep-link (`?entry=notification`) — calls `navigate('/', { replace: true })`.
- Because the effect has an empty dep array, it can only ever run once per JS context (i.e., once per real browser navigation/reload), so it cannot fire again from later in-app `<Link>`/`navigate()` calls within the same JS session.
- `sessionStorage` is empty on a brand-new tab/context but persists across an in-tab `F5` refresh — which is exactly the signal the fix relies on to distinguish "fresh boot" from "mid-session refresh."

## Methodology note on Scenario 1
A literal brand-new browser context/incognito profile does not share `localStorage` with the logged-in tab, so it would just show the login page (not a useful test of this redirect logic). Per the task's own fallback guidance, I used a single authenticated browser context/tab, explicitly cleared `sessionStorage` via `sessionStorage.clear()` (the same effective condition as a brand-new tab/PWA relaunch — empty `sessionStorage`, but authenticated via a still-populated `localStorage`), then did a hard reload while sitting on `/trainers`. This is a faithful simulation of the described "fresh sessionStorage while still authenticated" condition. Confirmed `localStorage` (`token`, `user`) remained populated across this reload — the user stayed authenticated throughout, so the redirect exercised is the fresh-boot path, not a login/logout artifact.

### Console output captured
```
error: Failed to load resource: the server responded with a status of 403 ()
error: [GSI_LOGGER]: The given origin is not allowed for the given client ID.
```
Both of these came from the Google Sign-In widget on the login page (`GoogleLogin` component in `LoginPage.jsx`) rejecting `http://localhost:5173` as an authorized origin for the configured Google OAuth client ID. This is a **pre-existing, unrelated** issue (Google Cloud Console OAuth client configuration), not caused by or related to the fresh-boot redirect fix. No errors were logged during any of the redirect/reload/navigation steps themselves.

## Overall Verdict: **PASS**

All three specified scenarios behaved exactly as intended:
1. A genuinely fresh boot (empty `sessionStorage`) while still authenticated on a non-root URL correctly bounces the user to `/`.
2. A same-tab refresh (which preserves `sessionStorage`, and thus the `appBooted` marker) correctly leaves the user exactly where they were — no disruption to normal mid-task refreshes.
3. Ordinary in-app navigation via the app's own nav links is completely unaffected — no unexpected redirects, no console errors tied to the fix.

## Recommendations (non-blocking)
- **LOW** — The pre-existing Google Sign-In origin/403 console errors on the login page are unrelated to this fix but are worth a separate ticket: register `http://localhost:5173` as an authorized JavaScript origin for the OAuth client, or suppress the widget entirely in local dev if Google login isn't exercised there.
- No issues found with the redirect fix itself; no code changes were made or are recommended.
